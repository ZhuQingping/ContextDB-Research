# ContextDB 团队共享价值与真实工程演示

2026年10月27日。面向产品价值汇报，使用本团队真实设计、排障和测试资料说明 ContextDB 怎样帮助新人完成工作。核心主张：**把专家在一次任务中形成的经验，变成团队成员及其 Agent 在后续任务中能够检索、核对和复用的知识。**

> 🧠 **From Hindsight memory (Hindsight)** — 项目采用工作空间与 Bank 一对一的模型；记忆 Recall 与知识页搜索是独立入口。这两项记录已对照当前设计、接口及本地实现核实。

## 汇报时先讲什么

建议这样开场：

“团队遇到一个问题，往往只有处理过它的人知道原因。其他人换个项目、换个会话，甚至换一个 AI 助手，还要重新问、重新查。ContextDB 把项目背景、设计决策、排障过程和验证经验沉淀为共享上下文。新人提出具体任务时，他的 Agent 可以找到团队已经确认的做法，说明依据和适用条件，帮助他更快完成开发、测试或排障。一个人的经验因此可以服务整个团队。”

“我们希望首先减少三件事：专家反复答同一个问题、新人重复踩已知的坑、不同 Agent 对同一规则作出不同解释。我们会用真实任务的完成时间、专家介入时间和错误率来检验这个价值。”

团队共享适合作为首个产品价值主线。它连接了明确痛点、现有能力和可测结果。但“共享”本身还不足以区分产品，必须展示知识怎样进入一次实际工作，并能回到原始证据。

## 从知识共享到任务复用

| 做法 | 对使用者的帮助 | ContextDB 演示应该证明什么 |
| --- | --- | --- |
| 共享文档与手册 | 有地方查资料 | 找得到相关内容，能读取来源。 |
| 按问题组织知识页 | 把多份资料组织成任务答案 | 不用自己从多个文档中拼出原因和做法。 |
| Agent 在工作中检索 | 上下文进入开发或排障过程 | 同一项目规则可以被另一个成员的 Agent 使用。 |
| 新经验整理后更新 | 团队经验随项目演进 | 补充证据后，刷新知识页并再次检索；关键规则需要人工确认。 |

与现有 Wiki、代码仓配合的合理方式是保留它们作为权威原件，ContextDB 提供面向任务的记忆、知识页及检索入口。优势成立的条件是接入工作流、保留来源与版本，并持续维护；如果只是多上传一批文档，价值会接近普通知识搜索。

共享给资深成员同样有价值：检视人可以复用曾经暴露的问题，测试人员可以复用风险与验证方法，值班人员可以复用诊断顺序。新人上手是直观入口，团队减少重复劳动才是长期收益。

## 五分钟怎么演示

1. **30秒说明困难。** 新人第一次接触项目，MCP可以连接，但服务日志出现`public.banks`不存在。单看这条报错，他可能去改客户端、建错表或索要管理员Key。
2. **45秒展示共享空间。** 打开四类知识页，说明它们来自开发、检视、测试和运维的真实资料，归属于一个项目空间。
3. **90秒完成新人问答。** 在“思考”入口输入：“我是刚加入团队的开发，MCP可以连接但日志报public.banks不存在。应该检查客户端还是服务端？如何修复、验证？”原演示还用新人只读凭据调用Reflect，复验需要恢复本机演示脚本及对应配置。
4. **60秒核对依据。** 打开“MCP 配置查询为何误入 public”和“权限变更应该怎样验证”。核对回答是否指出服务端适配、目标空间schema、工具发现与实际调用、版本和日志验证。演示答案应给出根据，不能声称当前服务一定仍有故障或已经完全修复。
5. **45秒展示另一人复用和权限。** 展示新人查询的实际响应、资料贡献者与新人的不同user_id，以及[权限检查（归档摘要）](verification-summary.md)：只读可以读取共享知识，写入和跨空间访问被拒绝。
6. **30秒说明后续循环。** 新问题解决后先由责任人核对事实，再更新来源资料并刷新相关知识页。这是建议的团队流程；本演示没有内置审批引擎，也没有自动修改生产规则。

同一批共享知识还可以支持不同角色的提问：

| 角色 | 演示提问 | 应核对的回答要点 |
| --- | --- | --- |
| 新开发 | 我应该把权限逻辑改在原生内核还是插件，为什么？ | 优先插件、保留原生过滤、认证与schema边界；具体修改仍需看代码。 |
| 新测试 | 我第一次测试权限变更，最少要覆盖什么？ | 正常读写、只读拒绝、未授权空间、MCP发现与调用；stub不代表真实模型验收。 |
| 新值班 | 健康检查正常，但知识页刷新失败，我先检查什么？ | 异步任务结果、模型429、配额与重试，区分PG就绪与模型可用。 |

面向领导时先展示角色提问及回答带来的帮助，再按需展开`public.banks`等技术细节。

原演示脚本及问答JSON已移至本机`.local-archive/2026-11-09-before-push/hindsight/product-value/team-sharing-20261027/`，不随仓库推送。需要重跑时，先恢复脚本和原演示配置，并核对空间、权限与服务版本；归档脚本不是当前代码仓维护的客户端工具。

原脚本的`query`使用Reflect，是一个单次示例；`check`查看知识页及复验权限。原始`newcomer-knowledge-search.json`与`newcomer-answer.json`保留在上述归档目录。模型是否采用知识页，应看实际响应证据，不能仅凭之前搜索过就断言采用。远端可读结果见[验证摘要](verification-summary.md)。

## 本次实测结果

四份资料写入完成，提取41条记忆，四个知识页均生成正文；已在真实浏览器打开。新人只读Key成功搜索和读取共享知识；同一Key尝试写入返回403，访问原有`contextdb`空间返回403。[验证记录（归档摘要）](verification-summary.md)

真实问答已完成：[阅读新人收到的回答（归档摘要）](verification-summary.md)。返回的`based_on.mental_models`明确包含“MCP 配置查询为何误入 public”和“MCP 报错与模型限流怎样分层排查”两个知识页的底层模型ID，因此本例有实际采用共享知识页的响应证据。

最终一次问答耗时27.52秒，服务报告输入11364、输出884、合计12248 tokens。本次前后两次问答合计48656 tokens，未包含资料提取、整理和知识页生成的成本。此次证明了跨用户知识复用，尚未证明Token或总成本节省。现场演示可先展示已保存的真实回答，再按时间决定是否重跑；不要保证每次都在27.52秒内完成。

最终回答已对照原料逐项核对，包含历史根因、插件修复方向、空间与当前消息身份、验证要点和来源，并区分源码与部署状态。它没有实际修改代码或执行修复验收。知识页和回答仍需团队责任人审核后才能作为正式操作规范。

## 用小范围试点检验价值

先选一个数据库研发团队，围绕20个高频真实问题，整理设计决策、踩坑复盘、测试与运维资料。建议试点两周，先人工筛选资料，再扩大自动采集。团队自行指定每类知识的维护人，发生版本变更时复核相应知识页。

对照实验应使用相同模型、任务要求和工具权限。让参与者完成难度相近且不重复的任务，一组使用现有文档和检索，一组增加团队ContextDB；交叉安排人员，避免熟练度和先做过任务的影响。由不知道分组的检视人核对答案、修改和验证结果。

| 指标 | 怎样记录 | 为什么有意义 |
| --- | --- | --- |
| 新人独立完成任务时间 | 从接题到通过既定验收，记录中位数及失败任务 | 是否更快形成可用交付。 |
| 专家介入时间 | 答疑、纠错、复核分钟数 | 是否减少反复解释相同背景。 |
| 已知问题重复发生率 | 按同一根因归类，统一时间窗 | 是否减少重复踩坑。 |
| 正确率与返工 | 盲评关键结论、适用版本、证据与遗漏项 | 防止只是回答更快却错得更多。 |
| 总调用成本 | 检索、写入、整合、生成的耗时和Token，加维护工时 | 判断节约是否覆盖新增成本。 |

开始前约定有效改善阈值，正确性与权限不能退化。召回一次不等于模型采用，更不等于节省一次专家答疑；即使未来上线召回统计，也需要任务层结果才能论证价值。

面向客户的付费理由是减少反复排查和交接成本、让多人多Agent使用一致的项目知识，以及具备可管理的访问边界。华为云托管交付的升级、可用性、容量和模型成本收益仍需目标环境证据支撑，不由本机演示推导。
