## 1. 结论与实施边界

最大的简化来自同一项需求收敛：**工作空间同步管理，删除及同名重建接受原生 Bank 的并发边界**。因此可以移除自研管理调度、执行登记、删除屏障、故障通知及其额外连接池，无须再建设替代框架。

删除前由管理员停止目标空间访问，等待已受理请求、原生后台任务和相关维护工作结束。不支持业务访问与删除并发；超时、取消或任务列表为空均不能单独证明执行者已经停止。不承诺并发删除重建没有旧写入，也不承诺跨进程缓存瞬时失效。完整约束见[设计规格](contextdb-release-design.md#feature-specification)。

| 项目 | 原实现 | 本轮本地实现 |
| --- | --- | --- |
| 管理 API | 14个方法与路径组合 | 13个，删除管理操作查询 |
| 管理表 | 8张 | 6张，删除两张调度/保护表 |
| 空间创建、删除 | 202受理，再查询管理操作 | 创建完成201，删除完成204 |
| 自研管理调度、租约、执行屏障 | 存在 | 移除 |
| 扩展运行时连接池 | metadata、admission两类额外池 | 普通元数据复用原生主库池 |
| 原生运行文件改动 | 7个 | 七项自研差异撤销，原生运行目录与官方基线一致；相关原生回归通过 |

表中数量不是工作量估算；原生运行文件恢复也不代表整个特性不再修改 UI、扩展、CI 或测试。

## 2. 已确认方向的实施清单

S01～S12、S14～S15已在本地实现；S13的测试依赖分组和构建层次收敛已修改，可信固定镜像免扫描仍为TODO。各项保留原实施范围及验收要求，完成实现不表示每项最终验收已经关闭。

### S01 工作空间管理改同步

- **修改范围：** 扩展 `http.py`、请求/响应模型、机器 OpenAPI、UI 代理和调用方。
- **具体处理：** POST 在初始化完成后返回201及空间；DELETE 清理完成后返回204。移除 `GET /ext/contextdb/v1/operations/{id}`、管理 `operation_id`、`latest_operation_id`、操作查询 Location 转换及强制 `Idempotency-Key`。
- **保留：** 空间列表/详情、必要状态、删除 `If-Match`、结果未知后的查询核对。POST 是严格创建，不继承原生 Bank PUT 的覆盖更新语义。
- **原生依据与最小适配：** 按[设计5.2.5.1](contextdb-release-design.md#native-bank-management-adaptation)沿用原生等待方式；移除自研空间创建/删除代理的固定15秒等待限制，部署入口超时按实际环境配置。超时/断连后核对普通空间资源，不新增管理可靠取消、续跑或自动重放机制。
- **验收：** 创建成功后可访问；重复创建409；删除缺条件428、旧条件412；超时不能被解释为必然回滚。原生记忆任务接口不变。

### S02 删除自研管理调度器

- **修改范围：** `lifecycle.py`、HTTP 扩展生命周期及相关配置、仓储方法和测试。
- **具体处理：** 移除任务领取、租约、续租、延期、自动重试、跨重启接续、终态操作保留和过期清理。剩余必要的创建/删除步骤组织为请求内函数，不保留一个空壳调度器。
- **配置清理：** 显式移除 `CONTEXTDB_OPERATION_RETENTION_HOURS`、settings和Repository的 `operation_retention_hours` 及所有传参、测试、文档，不留下无实际用途的操作历史保留设置。
- **保留：** 同步流程中的 schema 迁移、Bank 操作、状态记录和失败核对。部分失败仍占用名称，不接管残留 schema。
- **失败分支：** 以[设计5.2.5.1状态表](contextdb-release-design.md#native-bank-management-adaptation)为重新检视依据。复用原生事务、局部重试和best-effort文件清理，只适配初始化残留及schema/映射/授权；失败清理不承诺全局回滚、文件零残留或自动接续。
- **依赖与验收：** 与S01同批改造；进程启动后没有自研管理循环，原生内置 Worker 仍可正常处理记忆任务。不新增管理自动恢复平台。

### S03 删除增强执行登记和删除屏障

- **修改范围：** `admission.py`、扩展 Tenant/Validator/HTTP/MCP 接入，以及原生 Tenant、引擎和 Worker 的配套改动。
- **具体处理：** 移除持久在途登记、长事务持锁、提交/完整执行 scope、执行代次、`quiescent` 传播、未知故障屏障、排空专用查询及 Append 结束通知。
- **保留：** 动态认证、逐空间授权、schema 校验、内部任务的正常身份校验；原生取消、检查点、重试和最终状态更新。
- **拆分要求：** 先识别并迁出 Admission 中仍需使用的认证上下文、协议策略和脱敏逻辑，再删除保护实现。不可直接整文件删除，也不可用新表、触发器或中间件重建等效屏障。
- **内部授权：** 复用原生RequestContext和Validator，合法管理路由认证管理员后建立限定用途和目标的受信进程内上下文，替换操作ID/租约依赖；保留Worker正常身份检查，客户伪造Header或仅持Admin Key不能绕过原生Bank生命周期限制。不新增原生授权钩子或管理令牌，具体规则见设计5.2.5.1。
- **验收：** 正常 REST/MCP 权限和后台任务不退化；不再要求可靠 `workspace_busy` 或全局执行排空。并发删除原生复现作为行为记录，不作为必须修复的新增特性缺陷。

### S04 删除 MCP 故障通知链

- **修改范围：** 原生 `api/mcp.py`、`mcp_tools.py`，扩展 `mcp.py`、Admission 消费及专用测试。
- **具体处理：** 删除 `failure_reporter`、故障桥接、工具异常通知、scope 中通知的安装/恢复及仅用于屏障的 failed 标记。不另建 MCP 错误结果解析器作为替代。
- **保留：** 原生错误 JSON、日志及异步任务状态；当前消息认证、实际 Bank 解析、目录适配、逐空间权限和诊断脱敏。
- **依赖与验收：** 与S03同批。正常和异常工具结果保持原生协议行为，每条 MCP 消息仍重新认证，不能借复用会话跨空间越权。

### S05 合并连接池和关闭流程

- **修改范围：** 扩展 `tenant.py`、`admission.py`、`http.py`、`config.py`、部署渲染/意图模型、原生 `worker/main.py`。
- **具体处理：** 删除额外 `metadata_pool`、Admission 池、初始化锁、池所有权和关闭顺序分支；通过既有 Repository 适配复用原生主库池。移除独立 Worker 专为这些池增加的关闭调用。
- **删除配置：** `CONTEXTDB_METADATA_POOL_MAX_SIZE`、`CONTEXTDB_ADMISSION_POOL_MAX_SIZE`，以及对应 settings、`metadata_pool_max` / `admission_pool_max` 意图字段、模板和测试。
- **保留：** 原生池、可选只读池、迁移自有连接及原生关闭行为。元数据写入不走只读池，不新增原生池访问接口。
- **事务要求：** 短事务登记状态并释放连接 → 原生迁移/Bank 操作 → 短事务记录结果。不得持有管理连接或事务，再等待需要取连接的原生流程。
- **验收：** 管理 CRUD、业务调用和退出正常，没有剩余扩展运行时建池路径；实测共享池并发，不预先宣称性能提高。

### S06 删除两张管理表

- **删除：** `management_operations`、`request_admissions` 及仅服务于它们的索引、约束、触发器、注释、仓储方法和模型。
- **保留六表：** `deployment_info`、`workspaces`、`users`、`api_keys`、`key_workspace_permissions`、`audit_events`。
- **依赖：** S01～S05清除所有引用后收尾，不能在使用方仍访问时先删表。
- **版本边界：** 本期首次正式发布，结构版本仍为1；不为旧开发试验库增加兼容迁移。保留未来正式版本有序升级所需的版本管理。
- **验收：** 新建专用库初始化及重复初始化正常；DDL、OpenAPI和测试没有已删除表的有效引用。原生业务表结构不因本项变化。

### S07 简化 UI 操作恢复

- **修改范围：** 空间页面、管理调用层、操作查询代理及相应组件测试。
- **具体处理：** 删除管理进度轮询、退避定时器、查询进度入口、浏览器持久化的操作ID/幂等标识/旧请求恢复记录，以及依赖管理任务的恢复逻辑。
- **保留：** 提交中状态、重复点击防护、删除确认、错误提示；结果未知先查询资源并核对身份，不能自动重放删除或切换到同名新对象。
- **秘密处理：** Key 明文仍只展示一次，不写 localStorage/sessionStorage。不能将空间操作恢复的删除扩大为 Key 安全处理的删除。
- **验收：** 创建完成直接展示空间；删除完成更新列表；刷新和超时不会自动重放写请求，也不会误删同名新空间。

### S08 移除额外缓存代次跟踪

- **实施状态：** 额外UUID代次缓存及其调用已移除；保留原生TTL和缓存清理；本地相关回归已完成，结果见验证摘要。
- **修改范围：** Tenant 的 `_bank_generations`、`_refresh_bank_generation()`，仅用于它们的锁、容量管理及 HTTP/MCP/Worker 等调用点。
- **保留：** 原生缓存失效和 TTL，UUID 授权关联及对象条件。不再通过跨入口跟踪 UUID 宣称同名重建后缓存立即一致。
- **验收：** 普通配置读取和原生缓存清理保持；同名重建的跨进程瞬时一致不再作为首版保证。删除调用前核对其是否还承担其他正常职责。

### S09 从特性中拆出无关原生加固

- **具体处理：** 数据库连接日志脱敏从本特性差异中剥离，由[原生敏感日志 Issue #3](https://github.com/ZhuQingping/ContextDB-Research/issues/3)单独跟踪。
- **R06明确结论：** 回退本特性在原生URL日志脱敏函数及独立Worker连接日志中的自研改动。扩展API/UI已有错误脱敏和MCP诊断脱敏继续保留；这不是删除所有敏感信息保护。恢复原生仍保留已知敏感日志风险，独立修复是否随正式发行交付尚未确认。
- **文件目标：** S03/S04涉及的5个原生运行文件，以及 `utils.py`、`worker/main.py` 中本次新增的日志/额外池关闭逻辑，逐项核对并恢复原生对应行为。
- **验收：** 对官方基线检查实际 diff，说明剩余原生改动及必要性。不把独立问题恢复为原生行为描述为该问题已经修复，不机械还原其他仍有必要的修改。

## 3. 独立优化批次

以下条目按本轮实际进度区分已修改部分和剩余TODO，不作为恢复旧生命周期框架的理由。

### S10 同一请求复用认证结果

- 四个入口已经共用 `Repository.authenticate`，无需再造统一认证框架。
- MCP普通工具在可信适配层确定目标后完成一次目标认证，同一 Principal 用于权限和脱敏，减少无目标认证后再次目标认证。
- Validator 在同一目标 Principal 上检查角色、操作 scope，避免先 `authenticate_admin` 再重复目标认证。
- Admission 删除前拆出轻量认证上下文；复用严格限定为同一请求/消息、同一凭据、部署、目标Bank及空间UUID。
- `list_banks`、`tools/list` 等目录请求不能使用单空间 Principal 冒充完整目录权限。新请求和每条 MCP 消息重新认证，不增加跨请求凭据缓存。
- **验收：** 记录典型 REST/MCP 目标认证 SQL 次数；覆盖 Key 撤销、用户停用、角色、读写、跨空间和同名重建。减少查库不等于删除引擎权限校验。

### S11 复用 API 契约规则

- 集中维护条件请求解析、公共错误结构等重复规则；同步 OpenAPI、UI代理、curl示例与实际响应。
- API保留最终认证授权；UI代理保留登录会话、同源校验和固定上游目标；错误信息继续脱敏。
- 同步空间接口去掉管理操作响应后，清理对应类型和代理转换，不为减少重复引入大框架。
- **验收：** 缺失/错误/过期条件、未登录、业务Key调用管理接口及错误响应保持约定；不能仅检查生成文件相同。

### S12 收敛部署输入和首版交付分支

- **R04明确结论：删除 `CONTEXTDB_VALIDATION_LANGUAGE`。** 它当前是部署意图language的派生输出，不是第二个独立配置源；首版托管启动预检直接使用english，不再渲染或读取该环境变量。托管意图中的language不再作为客户选择项，按首版固定值处理；清理相关模板、配置合同和测试。不为替代它读取部署输入文件、扩大秘密挂载或新增参数；手工研究预检可保留显式 `--language`，原生全文配置变量不变。
- 首版固定单容器、API内置Worker及UI，固定 `native + english`；PGroonga、独立Worker等研究工具不成为默认初始化前提。
- 保留原生可选后端能力；不向客户暴露当前未交付的组合，不顺带安装替代中文全文插件。
- **验收：** 默认输入可部署并访问8888/9999，可配置端口；错误配置明确拒绝。中文输入/向量召回与中文全文验收范围明确区分。

### S13 收敛测试依赖和构建工作

- **本轮实现：** ContextDB系统测试采用显式contextdb依赖分组，收敛重复依赖约束并同步CI；不得只删lock、跳过故事测试或以单测代替端到端覆盖。
- **本轮实现：** 调整Dockerfile依赖安装、源码COPY及 `SOURCE_REVISION` 的作用域，减少后端改动造成的无关依赖/UI重建。
- **R05明确结论：不整体回退自研manifest及产物校验。** `artifacts.py::build_ui()`已经生成 `contextdb-release.json`，保留构建时生成和源码部署的源码/bundle匹配检查；只精简固定镜像启动时的重复全量扫描。固定镜像须由现有交付流程核对不可变镜像身份，且启动产物未被可变挂载替换；可变源码或产物路径仍执行匹配检查，不能仅凭任意manifest存在就跳过。**本轮状态：manifest生成及源码/bundle完整扫描均保留。现有启动流程尚无可信的不可变镜像与可变挂载证明，故不实施免扫描；该部分继续TODO。** 不另造签名/产物注册平台，不以环境变量或manifest存在跳过检查。运行时配置、秘密和实际服务检查仍保留。
- **验收：** 干净环境和缓存构建均成功，必需故事在CI实际执行，启动检查不因缓存失去有效性。系统字体用于离线构建，暂不删除。

### S14 统一两个工作空间创建入口

- **复现状态：** 2026-10-19已通过Chrome实际操作本地 `http://localhost:9999/dashboard`：打开顶部工作空间下拉列表，点击“创建新工作空间”，弹窗只有名称；关闭后点击Dashboard“创建工作空间”，弹窗有名称及描述。已用页面截图和可访问性树核对。本轮只打开/关闭表单，没有提交创建或删除，也未修改现有工作空间。
- **代码核对：** 两处均调用 `workspaceMutation("/workspaces", "POST", ...)`，共用UI代理 `POST /api/contextdb/workspaces`；下拉入口只传 `name`，Dashboard传 `name`、`description`。问题是重复前端表单的能力不一致，不是两个后端创建接口行为不同。代码位置为代码仓 `hindsight-control-plane/src/components/bank-selector.tsx` 的创建处理和弹窗，以及 `contextdb-workspaces-view.tsx` 的创建弹窗。
- **目标：** 两个入口均可填写工作空间名称和可选描述；字段说明、默认值、名称规范化、长度校验、错误提示和提交结果处理一致。

- **依赖：** 表单复用可独立实施；与S01/S07同批交付时统一采用同步成功响应，避免两个入口分别处理202和201。

- **复现状态：** 2026-10-19在同一Chrome页面实际确认Dashboard管理表格拥挤：现有短名称 `jiamu`、描述 `jiamu smile`、状态“正常”紧贴，表头“状态”和“操作”也贴在一起；左右仍有大量空白。无需长名称或大量工作空间即可复现。该短文本样例内容仍可读取，没有据此确认字符被截断或数据缺失；长文本、较窄窗口下的截断/遮挡仍列为后续验收。本轮没有复现下拉选择器拥挤，不能将Dashboard现象推广到全部列表。

### 7.2 R01：同步管理的超时与取消语义需补齐（重要）

- **对应条目：** S01、S07、S11。
- **代码依据：** UI管理代理 `hindsight-control-plane/src/app/api/contextdb/[...path]/route.ts` 当前使用 `AbortSignal.timeout(15000)`，所有管理上游请求固定15秒超时。
- **问题：** 改为同步创建/删除后，schema迁移或清理可能超过该时间。UI中止等待或代理返回错误时，后端仍可能继续执行；不能将其展示为确定回滚，也不能据此自动重新提交。
- **建议补充：** 测量创建/删除正常耗时，协调UI代理和部署入口的等待上限；区分明确失败与结果未知，定义后者的查询核对方式。明确客户端取消等待不等于服务端取消执行，不为解决这一点恢复管理任务表或自动排空平台。
- **补充验收：** 注入超过现有15秒的操作、代理超时和浏览器断连，确认不会自动重放写请求或误报回滚；已完成资源可通过普通查询核对。这里只验证管理请求的结果处理，不新增“全局执行已停止”的保证。

### 7.3 R02：失败状态、清理和人工重试合同仍偏抽象（重要）

- **对应条目：** S02、S06、S07及第4章必要状态。
- **问题：** 现有“保留状态、查询核对、部分失败继续占名”原则正确，但还不足以确定同步代码的错误分支。创建失败、部分删除、进程中断分别留下什么状态，哪些状态可以通过普通DELETE处理，哪些必须先停服务再人工清理，尚缺统一说明。
- **建议补充：** 给出最小状态转换表，列明初始状态、成功结果、明确失败、结果未知及允许的后续动作。特别覆盖“无Bank但仍有schema”“schema已清理但仍有空间元数据”“只剩部分初始化对象”等情况；记录足够的对象身份和失败信息即可，不增加租约、执行者登记或后台接管机制。
- **限制：** 中断状态继续占名，不因时间经过自动变为active或允许同名创建；普通重试不能接管同名新对象。人工清理的前提和对象核对方式写入运维手册，不以任务列表为空证明原执行结束。
- **补充验收：** 在元数据提交、schema迁移、Bank操作及最终清理之间注入失败或中断，检查状态、名称占用和人工处理结果；原ETag不能作用于同名新对象。

### 7.4 R03：同步生命周期调用的内部授权路径需明确（重要）

- **对应条目：** S02、S03、S10。
- **代码依据：** 当前 `hindsight_ext_contextdb/validator.py::_authorize()` 对内部创建/删除上下文检查 `ctxdb-internal-purpose`，并通过 `ctxdb-operation-id`、`ctxdb-lease-token` 和 `Repository.operation_is_owned()`核对执行权；`lifecycle.py`负责构造这份上下文。
- **问题：** 删除调度、操作表和租约后，现有合法管理调用也失去这条授权路径。只删除检查可能放宽原生Bank管理限制；保留原检查又会拒绝正常的同步管理操作。
- **建议补充：** 明确由已认证管理路由构造受信的进程内调用上下文，限定本次目标UUID、schema及操作目的，并与管理状态条件配合。客户可控Header或请求字段不能自行获得内部权限。无需另造管理令牌、租约或全程执行保护框架；普通Worker内部任务与管理生命周期调用分别保留必要的身份和schema检查。
- **补充验收：** 合法同步创建/删除可调用原生方法；管理员或业务Key从原生REST/MCP直接创建、删除、克隆等仍被拒绝；伪造内部用途字段、错误目标或跨schema调用不能绕过检查。

### 7.7 R01～R03更新：原生依据与最小适配（待重新检视）

**2026-10-19：** 按用户要求先走读官方v1.0.0，再决定新增资源的必要适配。原生事实与目标规则的完整说明已写入[设计5.2.5.1](contextdb-release-design.md#native-bank-management-adaptation)；本节用于下一轮检视定位，不代表实现或运行验证完成。

| 检视项 | 原生事实 | 本次更新后的实施范围 |
| --- | --- | --- |
| R01超时 | UI通过SDK等待Bank创建/删除，没有自研管理代理固定15秒限制；Bank接口直接await。Recall/Reflect/Retain的断连取消不覆盖Bank管理；数据库和运行环境仍有各自超时 | 去掉自研空间同步链路的固定15秒限制，沿用请求等待；入口配置由部署匹配。结果未知先查空间及身份，不自动重发、不承诺断连必停或必完成。不另建请求取消/恢复平台 |
| R02失败 | 核心创建/删除使用数据库事务；创建后配置/模板、删除后索引/文件不保证整体原子。索引失败可报错，文件失败记警告；没有普通Bank管理的持久恢复状态机 | 沿用这些原生行为，额外处理初始化残留及schema/空间映射/授权。最终PG清理放在同一事务；明确失败保留对象和名称，确认原调用结束后清理；结果未知不自动接管。仅保留必要空间状态与安全错误信息 |
| R03授权 | 普通请求走RequestContext→Tenant→操作Validator；服务端Worker构造internal上下文跳过客户Key认证，操作校验仍可执行。普通Bank管理不依赖操作租约 | 已认证管理路由使用现有上下文/Validator限定本次目的、UUID、Bank及schema；扩展内替换租约依赖。客户Header、Admin角色或internal标志单独都不能放行生命周期，Worker不取得额外管理权限 |

**新增资源的最小区别：** 原生删除不负责DROP独立schema及清理跨空间Key授权；这些由扩展补齐。原生PUT允许更新已有Bank，而空间POST仍严格创建。复用原生不取消空间UUID、If-Match、唯一约束和正常权限检查，也不将原生方法包进一个跨所有步骤的大事务。

**实现与验收重点：** 检查去掉15秒限制后的等待；检查超时/断连提示不误报回滚、不自动重发；检查失败保留对象、正常最终清理事务回滚和同名重建；检查合法管理上下文、客户伪造字段及普通Worker生命周期拒绝。原生不存在的全局排空、跨重启续跑、文件零残留、全链路原子回滚不作为新增通过条件。

下一轮只需重新审视这些规则及必要改动是否足够简单、正确；不要求先补齐原生并发删除缺口。原始R01～R03意见保留作讨论依据，本节与设计5.2.5.1是此次更新后的拟实施口径。
