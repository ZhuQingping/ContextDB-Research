## 3. 逐项整改条目

### 3.1 F1：合法分块读取返回 401

**问题是什么：** 已授权的 Key 可以写入和检索文档，却不能读取该文档的实际分块；管理员同样受影响。证据：源码确认、本轮离线认证链验证、原检视双 Worker 实测。

**复现步骤：**

1. 创建 `mysql_ops` 空间并签发 read_write、read Key；准备 Admin Key。
2. 用 read_write Key 写入测试文档，例如 document ID 为 `doc_part_1`，等待后台任务完成，确认 recall 成功。
3. 从实际业务返回值取得该文档的 `chunk_id`，不要用任意字符串代替实际分块。
4. 使用发布 Python SDK 调用 `client.documents.get_chunk(chunk_id)`；分别替换 read_write、read、Admin Key 重试。在 embedded-worker、standalone-worker 两种模式下执行。

| 当前行为 | 预期行为 |
| --- | --- |
| 返回 401：`Authentication failed: A registered Bank target is required` | 已授权读取返回对应分块的文本和归属；未授权空间或失效 Key 仍被拒绝 |

**原因与优化点：** 插件 `transport.py:125` 只为 Bank/文件下载路径建立空间上下文，直接放行 chunks；`tenant.py:62` 发现 `target_bank()` 为空后拒绝。原生 `MemoryEngine.get_chunk` 首先认证 Tenant，因此还没读分块就失败。

在自研插件识别 chunks 路径，复用原生 `parse_chunk_id` 确定 Bank，再执行已有认证、`bank_target` 和 `authenticated_request`，最后调用原生路由。保留引擎后续的 Bank/文档权限检查。不能删除 Tenant 的拒绝条件、默认指向某空间或遍历所有 schema 查分块；无需修改原生引擎、数据库和 SDK。

下划线必须使用原生编码：`mysql_ops`、`doc_part_1`、序号 0 会生成 `mysql~5Fops_doc~5Fpart~5F1_0`，不能简单 `split('_')[0]`。首版无存量实例，不为旧歧义格式增加跨空间查找；无法明确路由的输入安全拒绝，不重复 URL 解码。

**验收：** 实际 PG/API 与发布 SDK 完成上述双 Worker 正例；补充跨空间、无效/吊销 Key、无效/不存在 chunk、含下划线/转义字符、请求间上下文不串用等反例。read Key 仍不能写入。

**定位：** [transport.py](https://github.com/RSIXDB/hindsight/blob/1dc0ad37e/hindsight-extensions/contextdb-service/hindsight_ext_contextdb/transport.py#L125)、[tenant.py](https://github.com/RSIXDB/hindsight/blob/1dc0ad37e/hindsight-extensions/contextdb-service/hindsight_ext_contextdb/tenant.py#L62)、[原生 chunk 编解码](https://github.com/RSIXDB/hindsight/blob/1dc0ad37e/hindsight-api-slim/hindsight_api/engine/chunk_ids.py)。当前属于合法访问被拒绝，不定性为跨空间泄漏。

| 持续探测低优先级旧地址；一直不通时约 60 秒后退出 | 按当前设计优先使用 `CONTEXTBASE_CP_*`，就绪探测与 UI 运行读取同一有效配置 |

**优化点：** 修复已由 `49d727664` 落地到 `service.sh`、统一环境读取和相关探测调用。保留现有实现及测试，不重复重写启动流程；本项依据当前配置合同，不扩展为另一轮品牌改造。

**验收：** `test_environment.py` 与 `test_ui_probe.py` 覆盖单前缀、双前缀、显式空值等情况，本轮最终代码 38 项通过。该成绩不代表完整镜像或生产部署验收。

### 3.3 U1：表格与深浅色主题不一致

**问题是什么：** 管理表格的表头、背景、边线和行样式与已有控制台不一致，暗色下分隔线过强。属于一致性改进，不是“手写 table 必然有错”。证据：源码确认、原检视视觉实测。

**复现步骤：**

1. 等待工作空间列表、用户列表及展开后的 Key 表加载完成，分别查看浅/深色。
2. 与原生文档表格或公共 Table 的既有页面比较表头、边线、背景、行高及 hover。
3. 尤其观察新增表格的裸 `border`、`border-t`、`border-b` 在深色下的对比。

| 当前行为 | 预期行为 |
| --- | --- |
| 各管理表使用独立 table 样式，表头/边框与公共组件不同 | 同类表格使用统一主题 token 与信息层级；暗色边线不抢过正文，列宽仍适合各自内容 |

**优化点：** 在三个管理列表复用公共 Table 系列，统一 `bg-card`、边框颜色、表头与行反馈；保留工作空间长文本、Key 权限等专属布局。仅换 JSX 标签而不检查组合样式不算完成，也不为一张表改全局主题。

**验收：** 三种表格、浅/深色、默认/展开状态对照；长名称、长描述、权限列表正常，横向滚动仍可操作。

**定位：** `contextdb/workspaces-view.tsx`、`users-view.tsx`、`user-keys-panel.tsx`；公共 `ui/table.tsx`。

### 3.4 U2：目录布局不一致

**问题是什么：** 工作空间目录和用户目录的外边距、标题、工具栏及可用宽度不同，切页产生明显跳动。证据：源码确认、原检视视觉实测。

**复现步骤：**

1. 在同一个 1440px 浏览器窗口中先打开工作空间目录，再进入用户管理。
2. 页面加载完成后，比较标题/表格的左边界、主按钮位置、说明与工具栏间距。
3. 再检查 1024px 视口和有长描述的工作空间行。

| 当前行为 | 预期行为 |
| --- | --- |
| 工作空间页利用全宽；用户页 `max-w-7xl` 居中，页面组合规则不同 | 同类目录页的标题、内边距和工具栏有一致规则；工作空间目录继续满足设计要求的可用宽度 |

**优化点：** 统一目录页间距与标题层级，明确宽表容器的规则。不要只为对齐而把工作空间表一刀切成限宽；如果选择更改全宽设计，需要同时说明其对长文本和操作区的影响。

**验收：** 桌面/平板切页时标题与工具栏一致；宽表及长文本仍可读，不能用压缩业务列换取边界对齐。

**定位：** `contextdb/workspaces-view.tsx`、`users-view.tsx`；参照 `banks-overview.tsx` 的目录组合方式。

### 3.5 U3：搜索提示与分页展示不清楚

**问题是什么：** 搜索框缺少可见的用途提示；只有一页时仍出现两枚禁用翻页按钮，展开 Key 后再重复一套。已有 aria-label、后端 q 和分页，不能写成“搜索和分页功能缺失”。

**复现步骤：**

1. 用仅有 1～20 条记录的工作空间/用户目录，观察搜索框和翻页区域。
2. 输入存在的名称，确认请求携带 q、结果确实被过滤。
3. 展开只有一条 Key 的用户，观察子表仍显示的分页栏；再用多页数据作为对照。

| 当前行为 | 预期行为 |
| --- | --- |
| 搜索用途依靠位置/无障碍标签表达；单页显示禁用的上一页/下一页 | 提供明确搜索提示；单页显示简洁计数，多页时再显示可操作的翻页控件 |

**优化点：** 增加符合当前语言的 placeholder/必要图标，复用既有分页展示模式。保留 `total/limit/offset`、服务端搜索和翻页后范围，不新增另一套分页模型。

**验收：** 0 条、1 条、恰好 20 条、超过 20 条；带 q 翻页和清空筛选都正确。不能通过隐藏分页使第 21 条不可达。

**定位：** 三个管理列表的 Input/分页区；`ui/pagination.tsx` 仅作为组合参考。

### 3.6 U4：操作入口、按钮层级与文案不清

**问题是什么：** 用户行有两个相同的 Key 展开入口；危险操作强调不一致；创建和编辑都叫“保存”。这些是交互问题，不等于后端权限或确认流程失效。

**复现步骤：**

1. 用户行先点击左侧三角展开 Key，再点击右侧“管理 API Key”；观察同一面板又被收起。
2. 比较空间删除、Key 吊销和用户菜单删除的颜色与强调程度。
3. 分别打开创建 Key、编辑 Key，比较提交按钮文字。

| 当前行为 | 预期行为 |
| --- | --- |
| 两个入口调用同一 toggle；危险操作层级不同；创建/编辑共用“保存” | 展开入口语义明确；主/次/危险操作有一致规则；创建叫“创建”，编辑叫“保存修改” |

**优化点：** 合并重复入口或让入口承担清晰不同的动作；保留可访问的展开状态。统一行内操作用法，危险动作的最终确认继续明确，不通过随意修改公共 Button 默认外观替代页面设计。

**验收：** 点击与键盘展开一致；动作不会无故重复；危险操作仍需确认，提交中仍防止重复写入；中英文动词正确。

**定位：** `contextdb/users-view.tsx:219–287`、`key-editor-dialog.tsx`、`workspaces-view.tsx`、`user-keys-panel.tsx`。

### 3.7 U5：展开 Key 明细的信息过重

**问题是什么：** 用户下方的 Key 子面板重复标题、说明、刷新/创建、表头、完整 ID、时间和分页；少量数据也占据很大区域。行内展开本身符合设计，应保留。

**复现步骤：**

1. 打开用户管理，展开只有一条 Key 的用户。
2. 观察父列表与子面板重复的标题、操作栏、说明和分页。
3. 用有多个空间授权的 Key 对照，检查主要权限与辅助标识是否容易区分。

| 当前行为 | 预期行为 |
| --- | --- |
| 子面板接近一张独立完整页面，完整标识和辅助时间持续占位 | 先看清 Key 名称、脱敏值、范围/权限和主要动作；完整 ID、时间按需可查看 |

**优化点：** 简化子面板头部和说明，少量数据压缩分页，辅助信息折叠或弱化。缩略 ID 必须保留准确查看/复制入口，供结果核对；不能按名称或“最新一条”替代 ID。

**验收：** 一条/多条 Key 和大量授权均能查看；准确 ID 可取回核对；创建结果未知、编辑和吊销流程保持原目标身份。

**定位：** `contextdb/user-keys-panel.tsx:184–291`。

### 3.8 U6：Key 表单缺少空间搜索，控件不统一

**问题是什么：** 范围/权限使用原生 select，与公共 Select 外观不同；空间选择器只有每次 50 条加载更多，没有 q 搜索。搜索是设计第 5.4.2 节已要求的能力，现有分页并不缺失。

**复现步骤：**

1. 在独立实例准备至少 60 个 active 空间，给目标空间一个可辨识名称。
2. 创建或编辑 Key，选择“指定工作空间”，尝试直接输入目标名称查找。
3. 观察没有搜索输入；网络请求只有 `limit=50&offset=...`，无 q。点击加载更多仍可找到后续空间。
4. 比较范围/权限下拉框与控制台已有公共 Select；观察只读/读写说明是否有清楚分组。

| 当前行为 | 预期行为 |
| --- | --- |
| 用户只能分页找空间，控件与说明独立拼装 | 可按名称服务端搜索并继续分页；已选授权独立保留；控件和权限说明遵循现有规范 |

**优化点：** 在 `use-key-workspaces.ts` 增加 query，查询变化中止旧请求并重置 offset；使用后端 q，不只筛当前 50 条。已选项按 workspace_id 独立保存，搜索未命中不能删除授权或判空间失效。复用公共 Select，保留 all/selected 与 read/read_write 语义及名称单独编辑规则。

**验收：** 第 51 条后的目标可通过搜索找到；搜索/加载更多/清空搜索不丢选择；迟到响应不覆盖新查询；同名新 UUID 不自动继承旧授权；只读设置不被控件切换升级成读写。60 条样例只验证搜索/分页语义，不代表完成大规模性能验收。

**定位：** `contextdb/use-key-workspaces.ts:22–24`、`key-editor-dialog.tsx:181–281`。

### 3.9 U7：读取失败、无匹配和空数据混用

**问题是什么：** 组件初始数据为空，读取失败只设置 error，loading 结束后仍显示“没有数据”；搜索无匹配还显示不属于当前页面的建议。这会误导管理员对资源状态的判断。

**复现步骤：**
