# 核心价值：把工作经验交给下一次任务

**ContextBase 是给 Agent 使用的长期记忆服务，最终帮助人减少背景重述、经验流失和重复排查。** 人通过控制台管理空间、身份和内容；Agent通过接入组件存取经验。

## 先讲一个自然场景

你在公司用 Claude Code 排查订单通知问题，确认某种重试为何会重复入账，改代码并跑了测试。回家换电脑，用 Codex 继续做退款功能。

Git带来了代码，但“为什么选这个幂等键、哪些方案试过失败、原测试漏了什么”可能仍在旧聊天里。接入 ContextBase 后，新任务可以查到这些工作经验，再核对当前源码。换工具、换地点无需靠你重新讲一遍全部背景。

跨电脑是部署条件满足后的目标场景，本次已有实测是**同机不同Agent及不同成员身份**，尚未完成公司网络到家庭电脑的端到端验收。

## 三个核心卖点

| 卖点 | 原来遇到的困难 | 希望带来的变化 | 如何证明 |
| --- | --- | --- | --- |
| 项目经验跨会话、跨Agent复用 | 经验被锁在一次聊天或单一工具里 | 新任务能找回相关历史并给来源 | 新会话确实读到来源，接续任务通过独立验收 |
| 团队经验按权限共享 | 新成员重复问同一批背景问题 | 经授权找到前人复盘，知道从哪一步接手 | 独立只读成员查页成功，写入/越权读取失败 |
| 经验可追溯、可治理 | Agent说“以前如此”，却找不到依据 | 查看原文、时间与验证边界，纠正或失效错误内容 | 能从回答追溯文档，旧结论不会被当作实时状态 |

前两项已有本机案例；第三项中的来源与权限已有证据，但**错误结论被纠正后是否总能优先召回正确版本，尚未证明**。

## 为什么不能只靠模型或聊天历史

模型掌握通用编程知识，不会天然知道你项目昨天的决定。新会话即使有更长上下文，也需要选择哪些历史带进去。长期记忆服务负责持久保留和检索相关内容；Agent仍要判断和验证。

“自动”有前提：客户端采集接通、内容成功提交并处理、新任务实际检索。仅启动服务或仅注册MCP，不代表已经自动记住所有工作。

## 和现有工具是什么关系

| 工具 | 最适合保存什么 | ContextBase怎样配合 |
| --- | --- | --- |
| Git、源码、测试 | 当前实现与可执行行为 | 历史经验必须与当前代码核对 |
| AGENTS.md、CLAUDE.md | 稳定、明确、应共同遵守的规则 | 成熟经验可以沉淀为正式规则 |
| 文档知识库/RAG | 经整理的规范、手册、产品资料 | 工作经验补充尚未整理成文档的过程 |
| Agent自己的内置记忆 | 特定工具的上下文与偏好 | 在需要跨工具、共享和统一治理时评估集中服务 |

不宣称其它产品都没有长期记忆，也不把所有知识库能力都算成Hindsight独有优势。

## 哪些项目值得试

持续迭代的个人项目、多成员接手的团队、经常重复排障的运维工作，以及需要自己实现记忆循环的Agent应用。重点是**历史经验丢失带来的成本是否足够明显**。

一次性问答、现有规则与文档已足够、无需跨工具共享的任务，不必为了“有记忆”额外部署服务。

## 已证明与尚未证明

2026-11-05本机案例证明：正常工作可经过客户端采集，另一Agent能检索；共享知识能由独立身份读取，权限检查有效。订单有记忆与空记忆两侧均通过验收，未证明代码质量提升或提速。服务还有模型调用、检索延迟、存储与治理成本。

下一步衡量：接手任务时需要人补充多少次背景、重复尝试多少个已排除方案、结论能否追到有效来源，以及总时间和成本。详见[推进清单](05-backlog.md)。
