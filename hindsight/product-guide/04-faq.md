# 问题解答

更新：2026-11-08。客户端交互问题以本机已核对的版本和真实测试为依据；完整流程、时间线和源码见 [Codex与ContextBase交互说明](07-agent-knowledge-interaction-20261108.md)。本文区分已验证行为与后续优化，不把计划写成已完成。

## 是给人用，还是给Agent用？

主要给Agent提供长期记忆。人正常布置任务，通过控制台管理接入、内容和权限。最终受益者是人和团队。

## 我在公司、在家、换电脑、换Agent都能接上吗？

条件支持：旧工作已经成功采集；新环境可访问同一服务、同一项目bank；身份有权限；新Agent配置了检索。跨Agent已有本机证据，跨物理电脑/家庭网络尚待验收。代码用Git同步，记忆不等于同步未提交文件或运行进程。

## 用户每次都要说“请记住”吗？

配置了可靠采集后不需要。仅注册MCP不等于自动采集；ContextBase注册Hook负责接客户端会话生命周期。服务不会自行读取未接入的聊天。重要结论仍需核对是否实际存入。

## REST、MCP、SDK、CLI、Hook分别是什么？

| 方式 | 通俗解释 | 在接入中的作用 |
| --- | --- | --- |
| REST API | 服务提供的HTTP接口 | 提交、查询、管理等；Hook或应用可直接调用 |
| MCP | Agent调用工具的标准接口 | Agent发现和调用记忆工具；支持远程服务，也可有本地适配 |
| SDK | 开发者使用的语言客户端库 | 把接口调用封装成函数，具体覆盖能力取决于版本 |
| CLI | 人或脚本运行的命令行程序 | 配置、执行或管理入口；不等于单独的服务协议 |
| Hook/插件 | 嵌入Agent工作流程的接入组件 | 在合适时机采集和召回，内部可调用REST等接口 |

这些可以一起使用，不是必须五选一。不要把coding-agent插件、Python客户端、MCP客户端都统称为同一个HindsightClient。

## Codex客户端、Hook、MCP Server和大模型分别在哪里？

Codex客户端、ContextBase注册Hook、ContextBase MCP Server属于客户端侧，当前均运行在用户的Mac上。本文不再把“AI助手/Agent”与Codex客户端拆成两个组件；只在需要说明模型调用时单独列出LLM。

| 组件 | 负责什么 |
| --- | --- |
| Codex客户端 | 接收问题、管理上下文、调用后端大模型、执行Hook和MCP工具、显示回答 |
| ContextBase注册Hook | 插件注册的自动脚本，由Codex按会话事件执行，直接访问记忆服务REST接口 |
| ContextBase MCP Server | 本机mcp-server.js，由Codex启动，将MCP工具调用转换为记忆服务REST请求 |
| Codex后端大模型 | 为Codex生成回答及工具调用请求，具体工具由客户端执行 |
| ContextBase服务端 | 独立记忆服务，保存、检索和整理内容；自身另行调用配置的大模型与embedding服务 |

当前ContextBase服务也部署在同一Mac的8892端口，但属于独立服务，不代表必须与客户端同机。ContextBase用于Reflect、提取和整理的大模型调用，与Codex后端生成聊天回答是两条不同调用链。部署分组与流程图见 [统一交互文档](07-agent-knowledge-interaction-20261108.md)。

## ContextBase注册Hook就是CLI吗？它与MCP是什么关系？

本机三个Hook运行的是插件提供的Node.js脚本，由Codex自动启动；CLI是人或脚本在终端使用的命令入口，不能仅因同属一个安装包就混为一个组件。

两条路径分别是：

```text
按事件自动执行：Codex客户端 → ContextBase注册Hook → ContextBase REST API
按需使用工具：Codex客户端 → ContextBase MCP Server → ContextBase REST API
```

第二条路径的工具请求由Codex后端大模型产生、客户端负责执行。第一条路径不需要模型先决定是否调用。两者可同时生效，也可能一条正常、另一条失效。

## SessionStart、UserPromptSubmit、Stop何时执行？测试触发过吗？

| 事件 | 触发时机 | 本机主要行为 | 最新三轮测试 |
| --- | --- | --- | --- |
| SessionStart | 新会话初始化，可能在首次提问时完成 | 读取知识目录并提供使用说明 | 1次，成功返回3页目录 |
| UserPromptSubmit | 每次提交问题 | 按配置首次注入记忆、按节奏更新目录 | 3次；首轮Reflect约31秒成功，三轮目录均成功 |
| Stop | 每轮回答结束 | 保存本轮新增对话，跟踪异步任务 | 3次，任务全部完成，三份最终回答逐字匹配数据库 |

Stop不是“关闭客户端”，SessionStart也不等于每次启动应用就立刻执行。本机未注册SessionEnd，没有关闭窗口后另行保存一次的证据。完整图包含这三个阶段，见 [最新交互验证](07-agent-knowledge-interaction-20261108.md#latest-verification)。

## UserPromptSubmit选Recall还是Reflect，是Codex后端大模型决定的吗？

不是。**ContextBase注册Hook读取autoInject，由脚本固定分支选择接口。** 当前outer_space未显式设置该字段，使用默认reflect。成功结果缓存后通常不重复首轮正文注入；失败重试、新Bank延后等边界另由代码处理。

| autoInject | 首次自动动作 |
| --- | --- |
| reflect | 调用Reflect，取得服务端综合回忆 |
| recall | 调用Recall，返回记忆条目；插件默认查observation，可配置recallOptions |
| pages | 搜索知识页，取得片段 |
| none | 不自动注入上述正文，目录及工具说明按配置另行处理 |

Codex后端大模型可以随后决定使用MCP工具，这是另一条路径，不是它在Hook内部选择了接口。

## autoInject在哪里配置？默认reflect的代码在哪里？

这是客户端插件配置。outer_space的Hook通过CONTEXTBASE_CONFIG指定 coding-agent.json（本机现场路径：`/Users/zhuqingping/.contextbase/projects/outer_space/coding-agent.json`），autoInject是该JSON的顶层字段。示例仅展示字段，应合入现有对象，不要覆盖原API、Bank或凭据：

```json
{
  "autoInject": "reflect"
}
```

默认逻辑在 [core/config.ts的resolveAutoInject()](https://github.com/RSIXDB/hindsight/blob/dd5521cb948beff39a24d604f625bc4108d1aac2/hindsight-integrations/coding-agents/src/core/config.ts#L562)：有效的显式autoInject优先；否则旧配置autoReflect:false取none，其他情况取reflect。也可用CONTEXTBASE_AUTO_INJECT作环境后备值，文件中显式值优先。

hooks.json负责事件、脚本命令和超时，服务端api.env负责记忆服务配置；两者都不是当前项目autoInject的配置位置。

## Reflect超时后会直接降级Recall吗？

**先搜索知识页，未得到可用结果才Recall。** Hook遇到超时或服务端5xx等可降级错误时，按下面代码路径执行：

```text
Reflect
  ├─ 成功 → 注入综合回忆
  └─ 可降级错误 → 搜索知识页
                    ├─ 有可用内容 → 注入知识片段
                    └─ 无可用内容 → Recall检索memory
```

不能把所有4xx或空回答都当作超时降级。两项降级检索共享injectTimeoutMs预算，具体条件见 [Hook代码](https://github.com/RSIXDB/hindsight/blob/dd5521cb948beff39a24d604f625bc4108d1aac2/hindsight-integrations/coding-agents/src/core/hook.ts#L198)和 [完整决策图](07-agent-knowledge-interaction-20261108.md)。

## Recall与Reflect有什么区别？都查知识和memory吗？

这里“知识”指知识页/心智模型，“memory”指事实world、经历experience和观察observation。

| 比较项 | 独立Recall接口 | Reflect接口 |
| --- | --- | --- |
| 搜索memory | 可按类型查事实、经历、观察，并按需返回来源片段 | 内部可查观察、事实、经历及来源片段 |
| 搜索知识页/心智模型 | 不直接搜索这一类对象 | 可以 |
| 返回内容 | 相关条目、分数及可选来源信息 | ContextBase大模型结合检索结果生成的综合回答 |
| 模型处理 | 检索可能调用embedding，不生成综合回答 | 调用ContextBase配置的大模型推进查询与综合回答 |

注意同名差别：Reflect内部recall工具在当前版本只查world/experience；observation由search_observations处理。独立Recall API支持三类memory，不能用内部工具的限制代表整个接口。

## Reflect能否理解为Recall的超集？

可以理解为“检索加综合回答”的更高层能力，但不能认为结果集合一定包含一次Recall的所有结果。Reflect可先用知识回答，未必查原始memory，返回的也是归纳文本而非完整命中列表。

若需要条目、ID和筛选后的检索结果，用Recall；若需要根据项目历史综合解释，用Reflect。不能用“更高层能力”推断更快、更便宜或必定更完整。

## Reflect内部先查知识还是memory？谁决定继续检索？

**默认层级由服务端代码规定；满足提前放行条件后，才由ContextBase大模型判断是否继续。** 启用相关工具时，默认顺序为search_mental_models → search_observations → recall，分别对应知识、观察memory、原始memory。代码约束工具类型，模型生成查询参数，服务端执行。

允许解除继续查memory的强制要求，须同时满足：预算为low/mid；知识命中非空；所有命中明确is_stale=false；每项都有非空片段或正文。不是只看第一条，也不能把未知新鲜度当作最新。

解除后模型判断：知识够回答就生成答案，缺信息则读知识全文或补查memory。未解除时，继续按已启用的强制层级检索，仍受迭代、上下文、超时和错误边界限制。本次知识页过时，虽然budget=low，仍依次查了知识、观察和原始memory。源码与客户端/服务端分组决策图见 [07文档](07-agent-knowledge-interaction-20261108.md)。

## 为什么抓取中只看到知识页，没有看到Recall请求？

客户端POST /reflect后，ContextBase会在服务端内部检索memory；内部函数调用不会额外经过客户端代理。因此没有独立POST /memories/recall，不能推出没有查memory。

最新测试的服务端日志确认search_mental_models约245ms、search_observations约303ms、recall约184ms，检索合计约732ms；约31秒Reflect主要花在4轮服务端模型调用，最后返回950字综合回忆。响应based_on/trace为null，不能据这些耗时还原逐条命中ID。之后的MCP知识页搜索和全文读取是另一条路径。

## 知识页为什么显示过时，却没有失败调用？读取会自动刷新吗？

过时表示该页覆盖范围内有比上次读取水位更新的记忆，不表示调用失败，也不证明正文每句话已经错误。判断按标签、类型与更新时间，不先逐句判断文章是否受影响。

2026-11-08测试时，outer_space三个知识页采用手动刷新：refresh_after_consolidation=false，没有refresh_cron。新对话经过提取和观察整理后，页面可标为过时，但不会自动生成新版正文。读目录、搜索、读正文和Reflect都不能等同于刷新知识页。过时页仍可被检索读取；最新测试在此基线上执行，并未先刷新。

## Recall次数和最后召回时间能代表全部记忆使用情况吗？

不能。提交9a5ba2c6及当前版本明确统计“外部直接Recall或知识搜索的最终命中”，不是全部业务使用量：

| 行为 | 当前计数 |
| --- | --- |
| 外部Recall返回的memory | 计入 |
| 外部知识搜索返回的知识页 | 计入 |
| Reflect内部知识/memory检索 | 不计入 |
| 读取知识页全文 | 不计入 |
| 后台整理、知识页刷新 | 不计入 |

因此默认走Reflect时，memory虽被实际检索，其次数和最后时间仍可能不变；0或旧时间不代表未使用。统计有直接检索命中的意义，但不应展示为完整使用量。还要区分“命中”与“最终回答采用”，它们不是同一个指标。

已记录后续评估：保留原直接检索口径，考虑增加外部Reflect命中、知识全文读取等渠道，根请求内按对象去重，排除后台维护，不静默更改历史计数含义。详见 [统计设计与覆盖缺口](../design/contextdb-recall-usage-design.md)和 [推进清单](05-backlog.md)。状态为待设计、未实施。

## 客户端或协议变化，会不会影响客户业务？

可能。兼容升级通常可由插件/SDK更新吸收，Agent少写适配代码；但工具名称/参数、鉴权、客户端Hook事件、配置以及业务语义的不兼容变化，仍可能影响调用。重新注册MCP主要解决连接/工具发现配置，不能自动修复语义变化。

应固定服务与客户端版本，发布兼容说明，跑采集、召回、鉴权和跨Agent回归后再升级。不能承诺“只升级客户端，业务永远无感”。

## “事实、经历、观察”有什么区别？为什么这样区分？

**先记一句话：事实讲“外部世界是什么”，经历讲“Agent自己做过什么”，观察讲“从已有记忆中归纳出了什么”。**

这里的“观察”是整理后的认识，不是简单的“看见某件事”。三类也不完全平行：事实和经历主要区分视角，观察则是对来源记忆进一步整合的结果。

### 用同一个开发项目解释

以下为概念示例，不是新增的实际测试结果；具体分类还取决于输入角色、上下文和抽取。

| UI分类 / 类型 | 它回答什么 | 项目中的例子 | 怎样产生 |
| --- | --- | --- | --- |
| 事实 `world` | 关于用户、项目和外部世界，知道了什么？ | “项目用provider_event_id识别同一支付事件；用户要求重复投递不能重复入账。” | 从输入抽取有关规则、人物、事件等信息 |
| 经历 `experience` | 这个bank所代表的Agent，亲自做过什么？ | “我排查了并发重投报错，调整事务边界，执行了测试。” | 从Agent自身行动和交互记录中抽取 |
| 观察 `observation` | 这些信息综合起来，形成什么可复用的认识？ | “该项目的幂等处理要覆盖并发重投；只有顺序重复测试不足以证明并发安全。” | 后台整合有关事实/经历，形成有来源的归纳并随新证据更新 |

例子里的观察需要实际来源支持。不能因为一次报错就推断所有项目都会报错，也不能把“计划跑测试”归纳成“测试已通过”。

### 最容易混淆：谁的“经历”？

`experience`主要指**Agent自身的经历**，不是凡是某人讲过去的事都放这里。

- 用户说“我修复了登录故障”：应保留为关于这个用户的`world`事实，不能变成Agent自己修过。
- Agent的工作日志说“我修复了登录故障”：属于Agent自身的`experience`。
- 外部文章说“我做过某个实验”：应归给文章作者，不能记成当前用户或Agent做过。

所以不能只看有没有“我”字，需要明确说话者、材料来源和bank视角。这也对应此前视频里“把别人的经历记成我的经历”的风险：分类有帮助，但不能自动保证归因正确。

### 为什么不全部存成一种记忆？

1. **分清背景和行动。** “项目规定了什么”与“Agent实际尝试过什么”在接手任务时用途不同，不能混为已验证结论。
2. **同时保留细节与归纳。** 具体经历供追查当时发生了什么，观察供快速理解积累下来的经验；只留细节难找，只留总结容易丢依据。
3. **便于有针对性地检索。** 查规则、找曾经的尝试、了解长期模式时，可以选择相应类型，也可以一起查询。只查观察可能漏掉尚未整合的新经历。
4. **让认识能被修正。** 新证据可以支持或改变原有观察，同时仍需追溯原始来源和时间，而不是只留下一个无法核对的最终判断。

### 它们怎样联系？

```text
对话、工作日志、文档
          ↓ 抽取与归因
    事实 world / 经历 experience
          ↓ 后台整合（按配置与处理进度）
       观察 observation
```

不是每条事实都必须依次变成经历再变成观察；事实和经历是不同视角。观察也不要求固定积累多少条才可生成，粒度取决于配置和材料。整合可能异步，写入完成时观察未必已经更新。

### 观察与心智模型又有什么不同？

观察通常是后台整理出的一项认识，例如一条习惯或项目经验；心智模型则围绕指定问题，保存一份专题回答，例如“本项目支付通知处理完整指南”。知识页又把这类内容组织成便于浏览的文档。它们是不同层次的组织方式，不应理解成每条记忆必须经过的固定流水线。

### “事实”是不是就表示一定真实？

**不是。`world`是内容视角，不是可信度认证；`experience`也不是执行证明；`observation`更不是绝对真理。** 错误输入、错误归因和过度总结仍会留下错误记忆。判断可靠性还要看谁说的、原文、发生时间、工具或测试证据，以及是否存在后续纠正。

给领导讲可以用：“系统既保留项目背景，也保留Agent做过的事，再把相关内容整理成经验；这样接手时既能快速理解，又能回到来源核对。”

核对日期：2026-11-07。定义依据[官方Retain的分类说明](https://hindsight.vectorize.io/developer/retain#two-types-of-facts)、[官方Observations说明](https://hindsight.vectorize.io/developer/observations)及本地抽取实现。本节解释设计，不代表已经验证运行中实例每一条记忆都分类正确。

## UI知识页签里的“心智模型”是什么？

**可以把它理解为：围绕一个长期关心的问题，从已有记忆中整理并保存的一份专题总结。** 不是另一个大语言模型，也不是训练出一个新的模型。

例如，项目里有多次支付通知开发和故障排查记录。你定义一个问题：“这个项目处理重复支付通知有哪些约定，为什么这样设计？”Hindsight根据相关记忆生成总结，保存幂等键选择、事务边界、踩过的坑和验证范围。后续Agent可以读取这份已经整理好的内容，不必每次从全部历史重新归纳。

| 概念 | 通俗理解 | 例子 |
| --- | --- | --- |
| 原始记录/记忆 | 工作中发生过什么、留下哪些事实 | 某次并发重投抛异常，某次修复后测试通过 |
| 心智模型 | 针对一个问题汇总出的、可复用的理解 | “项目支付通知处理约定与已知限制” |
| 知识页 | 把这类整理结果组织成便于浏览的文档 | “研发指南/支付通知处理”页面 |

按当前官方文档和仓库设计，**知识页底层也是心智模型**，加上目录组织和适合文档的默认配置；不是两套完全独立的知识。心智模型强调问题、内容范围与刷新设置，知识页强调组织、浏览和使用。

创建/刷新需要基于已有记忆生成内容；读取已保存正文可避免每次重新生成。后续是否自动更新、何时更新取决于刷新配置和后台处理，不代表每条新记忆进入后页面立即变化，也不保证总结永远正确。

向领导可以这样说：“记忆记录以前做过什么，心智模型把这些经验整理成某个主题的长期总结，方便下一次直接接手。”

核对日期：2026-11-07。依据[官方心智模型说明](https://hindsight.vectorize.io/developer/mental-models)与本地`hindsight-docs/docs/developer/{mental-models,knowledge-pages}.mdx`；此处解释概念，尚未对运行中UI的创建、刷新与来源展示逐项验收。

## 为什么不直接用AGENTS.md或者知识库？

稳定规则适合AGENTS.md，正式手册适合知识库；尚未整理的日常取舍、排障和修正适合工作记忆。只需要固定文档检索时，现有RAG可能足够，不必额外引入服务。

## 团队是不是能看到所有人的对话？

不应该。可见范围取决于空间授权和实际采集内容；按项目/团队安排bank，成员用自己的业务Key。私人内容不要自动写入共享空间。API权限不约束PG超级用户或主机管理员。

## 记忆里的内容是不是正确答案？

不是。它可能是旧状态、Agent声明或错误推断。要看来源、时间、作者和验证条件，再核对代码/实时状态。已证明纠正可以存储，不代表旧错误自动删除或以后每次都会优先召回纠正。

## 写入成功就可以立即使用吗？

不一定。处理可能异步；operation completed说明提交内容已处理，不保证客户端提交了完整会话。要核对目标原文和领域事实，再验证新Agent检索。

## 客户端安装成功，为什么仍可能没有自动记忆？

MCP 连通、Hook 执行、会话完整保存需要分别验收。2026-11-07 安装排查发现：安装参数不自动构成目录到 Bank 的映射；用户级安装可能影响其他项目；多项目应使用独立的 `CONTEXTBASE_CONFIG`，并保证 Hooks 与 MCP 使用同一份项目配置。Codex 还需检查项目 Hooks 是否已信任、是否实际执行。

详细步骤与配置见 [客户端安装问题记录](../operations/contextbase-coding-agents-installation-issues-20261107.md)。该记录包含早期阶段的待验收状态；后续 outer_space 真实三轮会话已捕获自动提交与后台处理，MCP 调用也成功返回，但不代表所有客户端、所有项目均已验收。

## 深度回忆为什么超时？现在配置在哪里？

2026-11-07 的 outer_space 现场中，客户端约 20 秒就放弃首次 Reflect，而服务端仍在模型调用与重试。当前本机已调整为：单次模型 60 秒、服务端整次回忆 120 秒、客户端等待 150 秒、Codex 提问 Hook 180 秒。服务端值作用于 8892 实例，客户端值仅针对 outer_space。

[超时处理记录](../operations/contextbase-reflect-timeout-20261107.md)列出了三个配置文件的完整位置和实际键名。调整后先直接调用Hook成功一次（约18.6秒）；后续重新确认信任的真实桌面新会话，首轮Reflect约31秒成功，三轮保存及后台处理完成。**当前是本机调优，产品默认值尚未修改；是否采用为默认值见 [推进清单](05-backlog.md#客户端接入与回忆超时后续评估)。**

## 为什么接口保存成功，后台却报 embedding 错误？

2026-11-08 本机发现火山 embedding 单次最多接受 10 条输入，而适配器默认批量为 100，较大抽取批次因此返回 400 并导致后台 retain 失败。已把本机批量上限改为 10、重启实例，4 组受影响写入父子任务均已恢复完成；完整执行状态见 [embedding 批量超限处理记录](../operations/contextbase-embedding-batch-20261108.md)。HTTP 接收成功与后台完成必须分别检查。

## 为什么 MCP 正常，提问 Hook 却没有自动回忆？

2026-11-08 的真实三轮会话已确认 MCP 搜索和读取知识页正常，Stop 也自动保存了三份完整回答；但 UserPromptSubmit 的Codex客户端信任状态为 `modified`，没有发起预期的自动 Reflect 或每轮目录刷新。调整 Hook 配置（包括 timeout）后，应重新核对信任；`enabled:true` 和重启都不能代替 `trusted`。本次发现此前调高 timeout 后漏了这一步。详细请求、信任查询与源码核对见 [有知识页后的真实交互分析](07-agent-knowledge-interaction-20261108.md)。该轮自动注入未通过；后续重新信任后的 [真实三轮复验](07-agent-knowledge-interaction-20261108.md)已确认首轮约31秒Reflect成功及每轮目录更新。MCP成功仍不能单独替代Hook验收。

## Hook 不生效，为什么看不到服务端报错？

Hook 在Codex客户端侧就可能因为未信任、配置变更或禁用而没有执行，此时没有发请求，服务端自然没有对应失败日志。MCP与另两个Hook仍可能正常，用户也能继续聊天。目前不能仅凭“服务在线”或“MCP可用”确认自动记忆完整生效。我们已把独立自检、分环节状态、会话级执行证据及可操作提示列为 [P1优化项](05-backlog.md#优先优化hook-静默失效与客户端接入可观测性)，尚未实现产品自动发现。

## 为什么第二、第三轮没有再次自动深度回忆？MCP没工作吗？

成功的首次自动注入结果会缓存，后续通常不重复Reflect；降级取得的可用结果也可能缓存。失败且没有结果时还有有限重试等分支，因此不能说任何情况下都只允许首轮尝试。目录按配置更新，不等于每轮读取知识页全文。

MCP是否调用取决于Codex后端模型提出的工具请求，客户端负责执行。2026-11-07无知识页的测试，后两轮没有MCP调用；2026-11-08最新三轮则分别有3、1、2次，共6次。这是不同会话的实际选择，不能据任一轮无调用认定MCP故障。查询完整过程见 [统一交互文档](07-agent-knowledge-interaction-20261108.md)。

## 能保证节省多少时间或费用？

不能用现有小样本承诺。订单有记忆/空记忆两侧均通过，有记忆侧还更慢。本次证明经验可接续，收益需要测人补充背景次数、重复排障、总时间、模型成本和错误复用。
